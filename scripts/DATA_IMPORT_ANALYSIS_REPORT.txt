================================================================================
  SECTION 1: ARCHITECTURE OVERVIEW
================================================================================

The nucleIQ data import system is built on the following stack:

  Backend:
  - Django REST Framework API views in `backend/data_management/views_enhanced.py`
  - Template definitions in `backend/data_management/templates.py`
  - File parsing utilities in `backend/data_management/utils.py`
  - URL routes at: `/api/data-management/`

  Frontend:
  - React component at `frontend/src/pages/admin/DataManagement.tsx`
  - Upload flow: Select Module -> Download Template -> Fill Data -> Upload File ->
    Validate -> Import

  Key API Endpoints:
  - GET  /api/data-management/modules/              -> List all importable modules
  - GET  /api/data-management/modules/<module>/fields/  -> Field specs for a module
  - GET  /api/data-management/template/<module>/     -> Download template (xlsx/csv)
  - POST /api/data-management/validate/              -> Validate file (preview)
  - POST /api/data-management/import/                -> Import data
  - GET  /api/data-management/export/<module>/       -> Export data
  - GET  /api/data-management/import/<job_id>/status/ -> Job status

  Supported File Formats: CSV, XLSX, XLS
  Max File Size: 10 MB
  Max Rows Per Import: 5000

================================================================================
  SECTION 4: STUDENT PHOTO UPLOAD MECHANISM
================================================================================

  4.1) HOW IT WORKS
  --------------------------------------------------------------------------
  The student photo system uses a special ZIP upload path that is separate
  from the standard CSV/XLSX import flow.

  When module = "student_photos" and file extension = ".zip":
  - The ValidateDataView skips normal CSV parsing and calls _validate_photo_zip()
  - The ImportDataView skips normal CSV parsing and calls _process_photo_zip()

  4.2) EXPECTED FORMAT
  --------------------------------------------------------------------------
  - File: A .ZIP file containing student photo images
  - Image Formats: .jpg, .jpeg, .png
  - Naming Convention: Filename MUST be the student's admission_number
    
    Example ZIP contents:
      student_photos.zip
      ├── STU2024001.jpg
      ├── STU2024002.jpg
      ├── STU2024003.png
      └── STU2024004.jpeg
    
  - Subdirectories inside the ZIP are also handled (last path component is used)
  - System files (starting with '.') are ignored

  4.3) MATCHING LOGIC (from _process_photo_zip)
  --------------------------------------------------------------------------
  For each image file in the ZIP:
    1. Extract the filename: e.g., "STU2024001.jpg"
    2. Strip extension to get admission_number: "STU2024001"
    3. Look up: Student.objects.filter(tenant=tenant, admission_number="STU2024001", is_deleted=False)
    4. If found: Save to student.photo field using ContentFile
    5. If NOT found: Record error "Student STU2024001 not found"

  4.4) STEP-BY-STEP USER FLOW
  --------------------------------------------------------------------------
  1. Navigate to Data Management page
  2. Select "Student Photos" module
  3. Select a .ZIP file containing photos named by admission number
  4. Click "Validate" (system checks file validiy + matches students)
  5. Review validation results (matched vs unmatched)
  6. Click "Import" to apply photos to student records

  4.5) GENERATING DUMMY PHOTOS
  --------------------------------------------------------------------------
  To generate dummy photos, create a Python script that:
    1. Reads the student admission numbers from the generated CSV
    2. Creates simple placeholder images (colored squares or avatar PNGs)
    3. Saves them as {admission_number}.jpg
    4. Packs all images into a ZIP file
    
  See the generate_dummy_data.py script for an automated implementation.

================================================================================
  SECTION 6: VALIDATION RULES
================================================================================

  6.1) Built-in Validators (from utils.py)
  --------------------------------------------------------------------------
  - DateParser: Handles DD-MM-YYYY, DD/MM/YYYY, YYYY-MM-DD, Excel serial numbers
  - PhoneValidator: Strips +91/0 prefix, validates 10-digit Indian mobile
  - EmailValidator: Standard email format validation
  - DataTransformer: Module-specific transformations (e.g., gender normalization)
  - DataValidator: Module-specific row validation (students, staff, classes)

  6.2) Import Flow Validation
  --------------------------------------------------------------------------
  Step 1: FileParser.parse() - Parse CSV/XLSX/XLS into dict rows
  Step 2: DataTransformer - Normalize/clean data fields
  Step 3: DataValidator - Validate required fields, formats, choices
  Step 4: Duplicate check - Via unique_field against existing DB records
  Step 5: If errors found -> Block import, return errors
  Step 6: If only duplicates -> Require confirmation (skip/update)
  Step 7: Process import row by row with savepoints

  6.3) Error Handling
  --------------------------------------------------------------------------
  - Each row is processed in its own transaction savepoint
  - A failing row does NOT rollback other successful rows
  - All errors are collected and returned (limited to 50)
  - IntegrityError handling with duplicate fallback logic


================================================================================
  SECTION 7: QUICK REFERENCE - MINIMUM VIABLE IMPORT
================================================================================

  For getting a school system up and running, the minimum uploads needed are:

  1. classes.csv          -> Define grade levels and sections
  2. staff.csv            -> Define teachers and staff
  3. subjects.csv         -> Define subjects linked to grades
  4. students.csv         -> Define students (with class/section for auto-enrollment)
  5. fee_structures.csv   -> Define fee structures per grade
  
  That's it for basic setup! Everything else (attendance, exams, fees, etc.)
  is supplementary transactional data.
